# 要件定義書：えひめウォーククエスト

> 「歩く楽しさが、健康と愛媛の未来をつくる。」
> AI × 健康増進 × 観光活性化 × ゲーミフィケーション

## 1. はじめに

### 1.1 目的

えひめウォーククエスト（以下「本アプリ」）は、愛媛県の 2 つの地域課題に取り組むウォーキングアプリである。

- **課題① 健康増進**：ゲーム要素で運動への心理的ハードルを下げ、日常的に歩く習慣をつくる。
- **課題② 観光活性化**：有名観光地に加えて、知名度の低いスポットや商店街への訪問を増やす。

健康機能と観光機能は別々に作らない。歩く（健康）→ ポイント・アイテム（ゲーム）→ AI が観光クエストを提案 → 実際に訪問（観光）→ 限定アイテム・図鑑・ランキング → 翌日も歩く、という 1 つの循環として設計する。

### 1.2 対象コンテスト

愛媛県主催「えひめAI地域課題解決コンテスト」。評価項目は「リアリティ」「インパクト（スケーラビリティ）」「技術的根拠・地域への洞察」の 3 つ。

### 1.3 想定ユーザー

| ペルソナ | 主な動機 | 配慮事項 |
|---|---|---|
| 運動習慣をつけたい学生・社会人 | 無理なく続けたい | 過度な目標を出さない |
| ゲーム・着せ替えが好きな人 | 集める・飾る楽しさ | 課金要素なし。歩数で遊べる |
| 県内観光をしたい人・新しいスポットを探す人 | 行き先の提案がほしい | 希望時間と移動距離を優先 |
| 友達と競いたい人 | 比べる・応援する | 位置情報は公開しない |
| 高齢者 | 迷わず使いたい | 大きい文字・大きいボタン |

### 1.4 用語

| 用語 | 定義 |
|---|---|
| 歩数ソース | 歩数データの取得元。`demo`（デモ）、`healthkit`、`health_connect` |
| 信頼済み歩数 | サーバー側の検証を通過し、正式ランキングに反映できる歩数 |
| 週 | 日本時間（JST）の月曜 0:00 から日曜 23:59:59 まで |
| クエスト | AI またはシステムが提案する、観光スポットを含む散策プラン |
| 図鑑 | 「愛媛冒険図鑑」。訪問済みスポットと獲得アイテムの記録 |
| モック | AWS 未接続時にブラウザ内で動く代替実装。画面上で明示する |

### 1.5 フェーズ

| フェーズ | 内容 |
|---|---|
| 1. MVP | 画面一式、キャラクター、歩数表示、ポイント、ガチャ、着せ替え、ランキング画面、スポット一覧、AI クエスト提案（モック） |
| 2. AWS 連携 | Cognito、DynamoDB、Lambda、Bedrock、複数ユーザーランキング |
| 3. 観光強化 | GPS チェックイン、観光マップ、地域限定アイテム、図鑑、AI 観光ガイド |
| 4. 正式な歩数連携 | HealthKit、Health Connect、同期、不正対策 |
| 5. 品質改善 | UI/UX、性能、セキュリティ、実機テスト、デモ作成 |

## 2. 機能要件

受け入れ基準は「〜のとき、システムは〜する」の形で書く。各要件に対象フェーズを示す。

### 要件 1：画面構成とナビゲーション（フェーズ1）

**ユーザーストーリー：** 利用者として、主要な機能に迷わず移動したい。

1. システムは「ホーム」「冒険」「ガチャ」「ランキング」「マイページ」の 5 画面を持ち、画面下部の固定ナビゲーションから 1 タップで移動できる。
2. 現在の画面のナビゲーション項目は、色と形の両方で選択中と分かる。
3. 存在しない URL にアクセスしたとき、システムはホームへ戻るリンク付きの案内画面を表示する。
4. システムはスマートフォン縦画面（幅 360px 以上）を基準とし、タブレット（幅 768px 以上）では 2 列表示、パソコン（幅 1024px 以上）では左側メニュー + 2 列表示に切り替える。

### 要件 2：キャラクター作成（フェーズ1）

**ユーザーストーリー：** 利用者として、自分だけのキャラクターで冒険したい。

1. 初回起動時、システムはキャラクター作成画面を表示する。
2. 利用者はキャラクター名、髪型、髪色、肌色、目の色、初期衣装を選べる。
3. 選択肢は性別で分けず、すべての利用者がすべての外見を選べる。
4. キャラクター名が空、または 12 文字を超える場合、システムは保存せずに理由を表示する。

### 要件 3：キャラクター表示と着せ替え（フェーズ1）

**ユーザーストーリー：** 利用者として、集めた衣装でキャラクターを着せ替えたい。

1. システムはキャラクターを 2D ドット絵で表示し、パーツを重ねるレイヤー方式で描画する。
2. 装備スロットは「頭」「髪型」「上半身」「下半身」「靴」「アクセサリー」「背景」「ペット」の 8 つとする。
3. 利用者は所持アイテムだけを、対応するスロットに装備できる。
4. 着せ替え結果は保存され、次回起動時、ホーム、ランキング、プロフィールに反映される。
5. 装備によってポイント獲得量やランキング順位が有利になる仕組みは設けない。

### 要件 4：歩数取得（フェーズ1：デモ / フェーズ4：実データ）

**ユーザーストーリー：** 利用者として、自分の歩数をアプリで確認したい。

1. 歩数の取得処理は差し替え可能な「歩数プロバイダー」として実装し、Web アプリのデモ、iOS HealthKit、Android Health Connect を同じインターフェースで扱う。
2. すべての歩数記録は、日付（JST）、歩数、歩数ソース、同期日時を持つ。
3. 歩数ソースが `demo` のとき、システムは画面上に「デモデータ」と表示する。
4. 歩数ソースが `demo` の記録は、正式なランキングに反映しない。
5. 同じ日付の歩数を再同期したとき、システムは記録を上書きし、重複して保存しない。

### 要件 5：健康ダッシュボード（フェーズ1）

**ユーザーストーリー：** 利用者として、自分の歩く量の変化を簡単に確認したい。

1. システムは今日の歩数、週間歩数（月曜起点）、月間歩数、推定移動距離、推定消費カロリー、目標達成率、過去 7 日間の歩数グラフを表示する。
2. 推定移動距離と推定消費カロリーには「推定」であることと計算の前提を表示する。
3. 利用者は 1 日の歩数目標を変更できる。目標の範囲は 1,000〜20,000 歩とする。
4. システムは医療的な診断や治療の助言を表示しない。

### 要件 6：ポイント（フェーズ1：モック / フェーズ2：サーバー）

**ユーザーストーリー：** 利用者として、歩いた分だけポイントをもらいたい。

1. 歩数ポイントは 100 歩 = 1 ポイントとし、1 日あたり 10,000 歩分（100 ポイント）を上限とする。
2. ポイントの計算と残高の更新はサーバー側で行う（フェーズ1 ではモックサーバーが同じ規則で行う）。
3. 同じ日の歩数を何度同期しても、その日の付与済みポイントとの差分だけを付与し、二重付与しない。
4. 再同期で歩数が減った場合でも、付与済みポイントを自動で減らさない（減算は管理者による訂正として扱う）。
5. ポイントの増減はすべて取引履歴（理由・金額・日時）として記録する。
6. 歩数が少ない日でも遊べるよう、1 日 1 回のログインボーナスを付与する。
7. 1 日の上限に達したとき、システムは「今日はもう十分歩きました」のように休息を肯定する表示を行い、さらに歩くことを促さない。

### 要件 7：ガチャ（フェーズ1）

**ユーザーストーリー：** 利用者として、貯めたポイントで衣装を手に入れたい。

1. 通常ガチャは 1 回 50 ポイントで引ける。
2. 初期の排出確率はノーマル（N）60%、レア（R）30%、スーパーレア（SR）9%、ウルトラレア（SSR）1% とし、アプリ内に実際の設定値を表示する。
3. ポイントが足りないとき、システムはガチャを実行せず、不足ポイント数を表示する。
4. 抽選とポイント減算はサーバー側で 1 つの処理として行い、どちらか片方だけが成功する状態を作らない。
5. ガチャを引くとアニメーションを再生し、レア度に応じて演出を変える。
6. 獲得アイテムは自動的にインベントリに追加する。すでに持っているアイテムが出たときは重複して所持せず、代わりに 10 ポイントを返還する。
7. 演出を短縮・省略する設定を用意する（動きが苦手な利用者への配慮）。

### 要件 8：ランキング（フェーズ1：画面 / フェーズ2：複数ユーザー）

**ユーザーストーリー：** 利用者として、友達やほかの利用者と歩数を比べたい。

1. ランキングは「全ユーザー」「愛媛県」「フレンド」の 3 タブで切り替えられる。
2. 各行に順位、着せ替え後のキャラクター、ユーザー名、週間歩数、称号を表示する。
3. 「愛媛県」ランキングは参加を希望した利用者だけを対象とし、将来の市町別ランキングに対応できるデータ構造とする。
4. 週間ランキングは毎週月曜 0:00（JST）に締め、過去の順位を履歴として保存する。
5. 正式ランキングには信頼済み歩数だけを使う。
6. ランキングに位置情報や訪問先を表示しない。

### 要件 9：フレンド（フェーズ2）

1. 利用者ごとに一意のフレンドコードを発行する。
2. 利用者はフレンドコードで検索し、申請、承認、解除ができる。
3. フレンド同士は応援リアクションを送れる。リアクションは定型のものに限定する（自由文による嫌がらせを防ぐ）。

### 要件 10：不正対策（フェーズ4、MVP で保証する範囲を明示）

1. サーバーはクライアントから送られた歩数を無条件に信用しない。
2. サーバーは歩数ソース、同期日時、1 日の歩数の上限、同期間隔あたりの増加量を確認し、条件に合わない記録を「保留」にしてランキングから除外する。
3. 未来日付の記録と、一定期間（7 日）より前の日付の新規・更新記録は受け付けない。
4. HealthKit / Health Connect で手入力と判別できる記録は信頼済み歩数に含めない。
5. **MVP で保証できる範囲**：デモデータの除外、二重付与の防止、明らかな異常値の保留。端末を振るなどの物理的な水増しや、OS の健康データ自体の改ざんは完全には防げないことを利用者と審査員に明示する。

### 要件 11：観光スポットと観光マップ（フェーズ1：一覧 / フェーズ3：地図）

**ユーザーストーリー：** 利用者として、愛媛県内の行き先を探したい。

1. 初期実装のスポットは「松山城」「道後温泉本館」「今治城」の 3 か所とする。
2. スポットはスポット名、写真、説明、所在地、市町、座標、チェックイン状況、獲得できる限定アイテム、周辺スポット、情報源を持つ。
3. スポットデータは愛媛県 20 市町と他県へ拡張できる構造（地域コード・市町コード）で管理する。
4. スポットの説明は情報源（自治体・公式サイト等）を記録したうえで登録する。

### 要件 12：GPS チェックイン（フェーズ3）

1. 位置情報は利用者の許可を得て、チェックインボタンを押したときだけ取得する。常時追跡はしない。
2. 現在地とスポット座標の距離が、スポットごとのチェックイン半径に GPS の精度（誤差）を考慮した範囲内のとき、チェックインを成功とする。精度が極端に低い場合は再取得を促す。
3. チェックイン成功時、限定アイテムを付与し、図鑑を解放する。同じスポットの限定アイテムは 1 回だけ付与する。
4. 危険な場所や立入禁止区域への移動を促す表示をしない。スポットは安全に到達できる公開エリアに座標を置く。
5. 個人の位置情報は他の利用者に公開しない。サーバーにはチェックインの結果（スポット・日時）を保存し、生の座標は判定後に保存しない。

### 要件 13：愛媛冒険図鑑（フェーズ3）

1. 未訪問スポットはシルエットで表示する。
2. 訪問済みスポットは詳細情報、訪問日、獲得アイテムを表示する。

### 要件 14：AI パーソナル散策クエスト（フェーズ1：モック / フェーズ2：Bedrock）

**ユーザーストーリー：** 利用者として、自分の条件に合った散策プランを提案してほしい。

1. 入力は出発地点（現在地または指定地点）、希望散策時間、興味ジャンル、過去の歩数傾向、訪問済みスポット、希望する歩行負荷とする。
2. 出力はクエスト名、訪問先、散策ルート、推定所要時間、推定歩数、スポット紹介、獲得できるアイテムとする。
3. **訪問先は事前登録したスポットデータベースから選ぶ。** AI が返したスポット ID がデータベースに存在しない場合、その候補は破棄する。
4. 移動経路と所要時間は地図・経路検索サービスで計算する。経路が取得できない場合は「直線距離からの目安」と明示し、正確な徒歩ルートのように表示しない。
5. 希望時間と移動距離を、知名度の低いスポットの提案より優先する。
6. AI の呼び出しは 1 人あたり 1 日の回数上限を設ける。
7. Bedrock に接続していないとき、システムはモックの提案を表示し、画面上に「モック」と明示する。
8. AI から提案されたクエスト経由の訪問と、通常の一覧からの訪問を区別して記録する。

### 要件 15：AI 健康ミッション（フェーズ2）

1. 過去 7 日間の歩数をもとに、その週の 1 日の目標を提案する。
2. 提案する目標は、過去 7 日間の平均の +10%（最大 +1,000 歩）を上限とし、極端に高い目標を出さない。
3. 平均が 8,000 歩以上の利用者には、増加ではなく維持を提案する。
4. 利用者は提案された目標を受け入れずに、自分で変更できる。
5. 医療的な診断や治療の助言を行わない。体調不良時は休むよう案内する。

### 要件 16：AI 観光ガイド（フェーズ3）

1. スポットを選ぶと、AI がそのスポットの歴史、文化、特産品、周辺スポット、おすすめの散策方法を紹介する。
2. AI には登録済みの情報（情報源付き）だけを渡し、分かりやすく言い換えさせる。
3. 登録情報に無い内容は推測で断定しない。情報が不足する場合は「登録情報がありません」と伝える。

### 要件 17：AI 地域訪問促進（フェーズ3）

1. 有名スポットを含むクエストで、近隣の比較的知られていないスポット（商店街・文化施設など）を候補に含める。
2. 将来の地域事業者連携（店舗訪問型クエスト）に対応できるよう、スポットに種別（観光地・商店街・店舗など）を持たせる。

### 要件 18：マイページ（フェーズ1：表示 / フェーズ2：設定）

1. プロフィール、フレンド管理、歩数履歴、獲得称号、訪問履歴、アカウント設定を表示する。
2. アカウント設定で、愛媛県ランキングへの参加可否、ガチャ演出の短縮、歩数目標を変更できる。
3. 利用者はアカウントと関連データを削除できる。

### 要件 19：効果検証（フェーズ2〜）

1. システムは、利用日数、歩数目標達成率、週間平均歩数の変化、AI クエスト利用回数、AI 提案スポットへの訪問数、チェックイン数、継続利用率を集計できる。
2. 集計は個人を特定できない形（集計値、または少人数のセルを表示しない形）で出力する。
3. 実際に測定していない効果を、達成済みの成果として表示しない。デモデータは集計から除外する。

### 要件 20：根拠資料の記録（全フェーズ）

1. 地域課題・目標値・スポット情報の根拠（公開統計、自治体資料など）は、出典名・URL・確認日を `docs/evidence.md` に記録する。
2. 根拠が確認できていない主張は「未確認」と明記する。

## 3. 非機能要件

### 3.1 使いやすさ・アクセシビリティ

- 基本の文字サイズは 17px 相当以上。歩数などの重要な数値はさらに大きく表示する。
- タップできる要素は 48px 四方以上。
- 文字と背景のコントラスト比は WCAG 2.1 AA（4.5:1）を目標とする。
- 色だけで情報を伝えない（選択中のタブは色と形の両方で示す）。
- 動きを減らす OS 設定（`prefers-reduced-motion`）を尊重する。
- 主要な操作はアイコンと日本語ラベルの両方で示す。

### 3.2 性能

- 4G 回線相当でホーム画面の主要情報を 3 秒以内に表示することを目標とする。
- 通信中は読み込み表示を出し、失敗時は再試行ボタン付きのメッセージを出す。

### 3.3 セキュリティ・プライバシー

- AWS の認証情報や秘密鍵をソースコードに書かない。フロントエンドには公開してよい設定値（API の URL、Cognito のクライアント ID など）だけを環境変数で渡す。
- Bedrock はバックエンド（Lambda）からのみ呼び出す。
- ユーザーデータへのアクセスは、Cognito の認証情報から得たユーザー ID で制限する。クライアントが送るユーザー ID は信用しない。
- API の入力値をすべてサーバー側で検証する。
- ポイント、ガチャ、アイテム付与、チェックイン判定はサーバー側で行う。
- 個人の位置情報を公開しない。
- AI API に利用回数制限を設け、API Gateway でもリクエスト数を制限する。

### 3.4 コスト

- サーバーレス構成（Lambda、DynamoDB オンデマンド）を基本とし、利用が少ない時間帯の費用を抑える。
- Bedrock は低価格なモデルを優先し、生成結果を条件ごとに短時間キャッシュする。
- 利用料金の予算アラートを設定する。

### 3.5 拡張性（スケーラビリティ）

- スポット、地域限定アイテム、地域ランキングはコードではなくデータで管理し、他県へ展開できるようにする。
- 地域は「都道府県コード → 市町村コード」の階層で表す（全国地方公共団体コードを使用）。

### 3.6 保守性

- ゲーム規則（ポイント計算、ガチャ確率、日付計算）は副作用のない関数として分離し、フロントエンドのモックと Lambda で同じコードを使う。
- フロントエンドは API インターフェースを介してデータを取得し、モック実装と AWS 実装を環境変数で切り替える。

### 3.7 健康への配慮

- 過度な運動を促さない。1 日のポイント上限、休息を肯定する表示、目標の上限を設ける。
- 夜間や悪天候時の外出を促す通知を送らない。

### 3.8 権利関係

- 実在のキャラクター（例：みきゃん）や商標をアイテムやデザインに使う場合は、事前に権利者の利用許諾を確認する。許諾が確認できるまでは使わない。
- スポット写真は、権利者の許諾を得たもの、または利用条件を満たすものだけを使う。
