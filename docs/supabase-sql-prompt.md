あなたは Supabase（PostgreSQL 15 以降）とセキュリティに詳しいバックエンドエンジニアです。
次のアプリをオンライン化するための SQL を書いてください。いまはすべてブラウザ内のモック（localStorage）で動いており、これを Supabase に置き換えます。

## アプリの概要

- 名前：えひめウォーククエスト（愛媛県の健康増進と観光振興のためのウォーキングアプリ。Web アプリ、React + TypeScript、Vercel で公開）
- 遊び方：歩数でコインを貯める → ガチャで衣装を手に入れる → ドット絵キャラクターを着せ替える → 観光スポットでチェックインして限定アイテムをもらう → フレンドやランキングで競う
- 利用者は中高生〜高齢者。ログインの手間はなるべく少なくしたい

## いちばん大事な方針

1. **ゲームの値はサーバーが決める。** コイン残高、所持アイテム、ガチャの結果、チェックインの判定、クエスト報酬は、クライアントから直接 INSERT / UPDATE させない。すべて RPC（PostgreSQL の関数）を通し、関数の中で検証してから書き込む。
2. **全テーブルで RLS を有効にする。** クライアントが直接読めるのは自分の行だけ。他人の情報は、必要な列だけを返す関数（ランキング・フレンド一覧・フレンドコード検索）を通して見せる。
3. **二重付与を防ぐ。** 同じ報酬は一意制約で 1 回しか入らないようにする（連打・同時実行でも二重にならない）。
4. **位置情報を保存しない。** チェックインの判定には座標を使うが、テーブルには保存しない。ログにも出さない。他の利用者に訪問先や位置を見せない。
5. **デモ用データは正式ランキングに入れない。**
6. フロントエンドは anon キーだけを使う。service_role キーは使わない前提で設計する。

## 認証

- Supabase Auth を使う。最初は**匿名サインイン**で始め、あとからメールアドレスを結び付けられるようにする（アカウントを引き継げるように）。
- ユーザーの行はすべて `auth.users(id)` を参照し、`on delete cascade` にする。
- 新しいユーザーができたら、プロフィールの行を自動で作る（トリガー）。フレンドコードもこのときに発行する。

## データと規則

### プロフィール・キャラクター
- プロフィール：ユーザー名（1〜12 文字、前後の空白は除く）、フレンドコード、地域（都道府県コード、既定 `'38'` = 愛媛県）、愛媛県ランキングに参加するか（既定 true）、表示中の称号 ID、1 日の歩数目標（1,000〜20,000、既定 6,000）、キャラクター作成済みか、ガチャ演出を短くするか、デモ用アカウントか、作成日時
- フレンドコード：8 文字。使う文字は `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`（紛らわしい 0 O 1 I を除く）。全体で一意。検索時は小文字・空白・ハイフンを許して正規化する
- キャラクター：名前（1〜12 文字）、見た目（髪型 `short|bob|long`、髪色 `black|brown|mikan|blonde|seto|pink`、肌 `light|medium|tan|deep`、目 `brown|black|blue|green`）、装備（場所 `head|hair|top|bottom|shoes|accessory|background|pet` ごとに 1 つのアイテム ID、空も可）
- キャラクター作成（onboarding）：名前・見た目・最初の上下の服（決まった初期衣装の中から選ぶ）を受け取り、初期衣装を所持品に入れて装備する。作成済みなら 2 回目は受け付けない
- 装備できるのは自分が持っているアイテムで、アイテムの場所（slot）が合うものだけ

### 歩数とコイン
- 歩数は日付（**日本時間**の YYYY-MM-DD）ごとに 1 行。取得元 `device_motion|demo|healthkit|health_connect`、検証状態 `trusted|pending|excluded`、デモ操作で足した歩数（別の列）、最後の同期日時
- 同期の RPC：直近 7 日分（今日を含む）の日付だけ受け付ける。未来の日付、7 日より前、負の値、1 日 100,000 歩を超える値は拒否する。同じ日付は「大きいほうの値」で更新する（減らさない）
- 検証状態：`device_motion` は `pending`、`demo` やデモ操作で足した歩数を含む日は `excluded`。`trusted` はネイティブアプリ化（HealthKit 等）までは使わない
- コイン：**100 歩 = 1 コイン**。1 日の上限なし。日付ごとに「すでに付与した歩数ポイント」を覚え、増えた分だけ付与する（何度同期しても二重にならない）
- コインは**取引の履歴（台帳）**で持つ。理由 `step_reward|login_bonus|gacha_draw|gacha_refund|demo_grant|admin_adjustment|quest_reward`、金額（正負）、参照キー、日時。残高は台帳と食い違わないようにする（残高の列を持つ場合は、同じトランザクションで更新し、0 未満にしない）
- ログインボーナス：1 日 1 回 10 コイン（日本時間で日付が変わると再び受け取れる）

### ガチャ・アイテム
- 1 回 50 コイン。残高不足なら拒否
- レア度の確率：N 60% / R 30% / SR 9% / SSR 1%。レア度を決めたあと、そのレア度でガチャから出るアイテムの中から同じ確率で 1 つ選ぶ。乱数はサーバー側で作る
- すでに持っているアイテムが出たら、所持は増やさずコインに変換：N 5 / R 15 / SR 30 / SSR 50
- 所持アイテムは「ユーザー × アイテム」で一意（重複して持たない）。手に入れた日時と入手方法（`starter|gacha|spot|login_bonus`）を持つ
- アイテムのマスタ（ID、名前、場所、レア度、入手方法、ガチャから出るか）はテーブルにし、添付の `items.ts` から INSERT 文を作る。ガチャの結果を返すとき、引く前の残高・使ったコイン・変換されたコイン・新しい残高も返す

### 称号
- 条件はサーバーで判定し、獲得していない称号は選べないようにする
  - `mikan_novice` みかん見習い：はじめから
  - `gacha_debut` ガチャデビュー：ガチャを 1 回引く
  - `steady_walker` コツコツ歩き：直近 7 日間で歩数目標を 3 日達成
  - `first_journey` はじめての旅人：観光スポットに 1 か所チェックイン
  - `ehime_explorer` 愛媛冒険家：観光スポットに 3 か所チェックイン
  - `collector` おしゃれコレクター：アイテムを 10 種類集める

### 観光スポットとチェックイン
- スポットのマスタ（ID、名前、市町コード、座標、チェックイン半径 m、タグ、限定アイテム ID）はテーブルにし、添付の `spots.ts` から INSERT 文を作る。誰でも読める
- チェックインの RPC：スポット ID、緯度、経度、GPS の誤差（m）、経由（`ai_quest|list`）、クエスト ID（任意）を受け取る
  - 誤差が 200 m を超えたら判定しない（`low_accuracy` を返す）
  - 現在地とスポットの距離（ハバーサイン式でよい。PostGIS は使わなくてよい）が「半径 ＋ min(誤差, 50 m)」以内なら成功、外なら `too_far` と距離を返す
  - 成功したら訪問を記録する（スポットごとに初回だけ。日時・経由・クエスト ID・GPS で確認できたか）。**座標は保存しない**
  - 初回の訪問だけ、そのスポットの限定アイテムを所持品に入れる
  - `ai_quest` 経由と記録してよいのは、そのクエストがサーバーで本人に提案した記録があり、そのスポットを含むときだけ。そうでなければ `list` として記録する

### フレンド・応援
- フレンドコードで相手を検索できる。返すのはユーザー名・キャラクター・称号・自分との関係（`none|friend|pending_sent|pending_received|self`）だけ
- 申請・承認・見送り・申請の取り消し・解除ができる。相手からすでに申請が来ている人に申請したら、そのままフレンドになる。自分には申請できない。フレンドは最大 100 人
- フレンドにだけ今週の歩数を見せる（申請中の相手には見せない）
- 応援：フレンドにだけ、種類 `nice|fight|thanks` を送れる。送りすぎを防ぐため、同じ相手には 1 日 3 回まで

### ランキング
- 週は**日本時間の月曜 0:00 から**。今週の歩数の合計で並べる
- 範囲：全ユーザー / 愛媛県（愛媛県ランキングに参加している人だけ） / フレンド（自分と承認済みのフレンド）
- **正式ランキング**は `trusted` の歩数だけ。**Web 版ランキング**は `trusted` と `pending` を合わせた歩数で、画面に「端末のセンサーの推定値」と表示する。`excluded`（デモ）はどちらにも入れない。デモ用アカウントも入れない
- 返す列：順位、ユーザー ID、ユーザー名、キャラクター（見た目・装備）、称号名、今週の歩数、自分かどうか。上位 100 人まで
- 自分の情報も返す：今週の歩数、対象かどうか、対象外の理由（`demo_data|unverified|not_opted_in`）、対象外なら自分の歩数で何位に当たるか（参考）
- 利用者が増えても重くならない作りにする（インデックス、必要なら週ごとの集計テーブル）

### みんな共通のクエスト
- 定義（添付の `commonQuests.ts`）：
  - `daily_3000`：今日 3,000 歩、毎日、20 コイン
  - `weekly_30000`：今週 30,000 歩、毎週、100 コイン
  - `community_weekly`：参加者みんなの今週の合計 500,000 歩、毎週、50 コイン。自分が今週 1,000 歩以上歩いたときだけ受け取れる
  - `matsuyama_history`：松山城と道後温泉本館を両方訪問、1 回だけ、150 コイン
  - `ehime_first_step`：松山城・道後温泉本館・今治城を訪問、1 回だけ、300 コイン
- 進み具合を返す RPC と、報酬を受け取る RPC。受け取りは「クエスト ID × 期間キー（毎日なら日付、毎週なら週の月曜、1 回だけなら `once`）」で一意
- 「みんなの合計」は、全ユーザーの今週の `excluded` 以外の歩数の合計。参加人数も返す

### AI 散策クエストの回数
- AI の提案は 1 人 1 日 5 回まで（日本時間で日付が変わると戻る）。回数を 1 つ予約する RPC と、AI の呼び出しが失敗したときに 1 つ戻す RPC
- AI が提案したクエストの記録（クエスト ID、ユーザー、スポット ID の一覧、作成日時、モデル名）も残す。チェックインの「AI 経由」の判定と効果検証に使う
- いまの公開版では、AI の回数は Vercel Functions のメモリで数えていて目安にしかならない。これを Supabase で正確に数えられるようにしたい（Vercel Functions から呼ぶ想定。どの鍵で呼ぶのが安全かも提案してほしい）

### デモ操作（発表用）
- コインを足す（+100 / +500 / +1,000）、今日の歩数を足す（+100 / +1,000 / +5,000 / +10,000）。**デモ用アカウントにだけ許可する**
- デモで足した歩数とコインは、通常の歩数・コインと区別して記録し、その日の歩数は `excluded` にする

### データ削除
- 自分のデータをすべて消す RPC（プロフィール以外の全テーブル。プロフィールは初期状態に戻す）。Auth のユーザー自体の削除は、管理者の処理が必要なら、その方法を説明する

### 効果検証（任意）
- 利用した日、AI クエストの生成、AI 経由の訪問、一覧からの訪問、チェックインを、集計しやすい形で残す。個人を特定しない集計用のビュー（少人数の集計は出さない）

## 出力してほしいもの

1. **1 つの SQL ファイル**（Supabase の SQL Editor に貼ってそのまま実行できる。上から順に実行して通る。2 回実行しても壊れないとうれしい）
   - 型（enum または check 制約）→ マスタ → ユーザーデータのテーブル → インデックス → RLS とポリシー → トリガー → RPC → マスタの INSERT の順
   - コメントは日本語
   - RPC は `security definer` にし、`set search_path = ''` を付け、テーブル名はスキーマ付きで書く。中で必ず `auth.uid()` から本人を決め、引数でユーザー ID を受け取らない
   - 実行してよいのは `authenticated` ロールだけにし、`anon` と `public` からは実行権限を外す
   - ゲームの値を変えるテーブルは、クライアントからの insert / update / delete のポリシーを作らない
   - エラーはクライアントで扱いやすいように、決まったコード（例：`insufficient_coins`、`already_claimed`、`invalid_input`、`not_found`）で返す
2. **RPC の一覧表**（関数名・引数・戻り値・どの画面の操作か）
3. **フロントエンドからの呼び出し例**（`supabase-js` v2 の `supabase.rpc(...)` で 3 つほど）
4. **動作確認用の SQL**（2 人のユーザーを想定し、RLS で他人の行が見えないこと、ガチャの連打で二重に引けないこと、同じ報酬を 2 回受け取れないことを確かめる手順）
5. **決めきれなかった点・前提にした点**の一覧
